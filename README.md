# gost-pfx-divider

[![selftest](https://github.com/alexkudelin/gost-pfx-divider/actions/workflows/selftest.yml/badge.svg)](https://github.com/alexkudelin/gost-pfx-divider/actions/workflows/selftest.yml)

Разделение PFX-контейнеров (PKCS#12) с ключами и сертификатами, выпущенными по алгоритмам ГОСТ Р, на приватную и публичную части. Вся работа происходит в Docker-контейнере — в хост-систему ничего не устанавливается.

*Read this in [English](README.en.md).*

```
make split PFX=ivanov.pfx
```

```
results/ivanov/
├── private.key   приватный ключ, PEM, без пароля
└── public.cer    сертификат владельца, PEM
```

## Проблема

PFX, выданный удостоверяющим центром и выгруженный из КриптоПРО CSP, обычным `openssl` не открывается:

```
$ openssl pkcs12 -in ivanov.pfx -nokeys -out public.cer
Error outputting keys and certificates
error:0308010C:digital envelope routines:inner_evp_generic_fetch:unsupported:
  Algorithm (RC2-40-CBC : 0), Properties ()
```

Причин у этого сообщения обычно две, и они срабатывают одновременно:

1. **Внутри контейнера — ГОСТ.** Ключ и сертификат используют ГОСТ Р 34.10-2012 и ГОСТ Р 34.11-2012, которых нет в штатном OpenSSL. Нужен [gost-engine](https://github.com/gost-engine/engine).
2. **Снаружи контейнер завёрнут в старый PBE.** КриптоПРО CSP при экспорте до сих пор шифрует мешок с сертификатами через `pbeWithSHA1And40BitRC2-CBC`, а OpenSSL 3.x вынес RC2 в *legacy provider*, который по умолчанию выключен.

Отсюда и репутация «не разделяется ничем»: включив что-то одно, вы получаете ту же ошибку, просто в другом месте. И отсюда же классический способ выстрелить себе в ногу — собрать патченый OpenSSL и подменить им системный. На большинстве дистрибутивов от системного `libssl` зависит примерно всё, от `apt` до `ssh`, и такая замена ломает базовый набор софта надолго.

## Ценность

**Разделение нужно сделать один раз — дальше работают штатные средства.**
Это главное. PKCS#12 требует ГОСТ-совместимого разбора контейнера каждый раз, когда его открывают. После разделения на руках остаются два обычных PEM-файла, а их любое приложение принимает своими штатными опциями — `ssl_certificate_key` в nginx, `--cert`/`--key` в curl, пути в конфиге сервиса, имя файла в скрипте. Ни патчить OpenSSL на боевом хосте, ни таскать за собой gost-engine, ни разбирать PKCS#12 в рантайме больше не нужно.

**Хост-система остаётся чистой.**
ГОСТ-софт живёт внутри образа и умирает вместе с контейнером. Системный OpenSSL не трогается вообще — ни `LD_PRELOAD`, ни правки `/etc/ssl/openssl.cnf`, ни `make install` в `/usr/local`.

**Коробочное решение.**
Два make-таргета и никакой настройки: `make build`, `make split PFX=...`. Не нужно помнить ни набор флагов `openssl pkcs12`, ни то, как включается engine в конфиге.

**Годится для закрытого контура.**
Образ собирается один раз на машине с интернетом и переносится (`docker save`/`docker load`) на сервер, где сети нет. Само разделение выполняется с `--network none` — контейнер физически не может ничего никуда отправить.

**Пароль не утекает в историю процессов.**
Он передаётся в контейнер через stdin, а не аргументом командной строки и не через `docker run -e`: и то и другое видно в `ps` и в `docker inspect` любому, кто имеет доступ к хосту.

### Оговорка

Это простое решение, найденное эмпирическим путём. Никакой новизны в нём нет: внутри — те же самые команды `openssl pkcs12`, которые можно набрать руками. Ценность только в удобстве и в том, что правильная комбинация engine, provider и флагов уже подобрана и зафиксирована.

Отдельно стоит понимать границу: разделение делает файлы читаемыми для любого приложения, но не учит приложение ГОСТ-криптографии. Если вам нужно именно ГОСТ-рукопожатие TLS, поддержка ГОСТ всё равно должна быть на стороне клиента или сервера. Для всего остального — передать ключ в подписывающую библиотеку, положить в хранилище секретов, сконвертировать, отдать сервису — разделённых PEM достаточно.

## Требования

* Docker
* `make`

Больше ничего. OpenSSL 3.5 и gost-engine собираются внутри образа.

## Быстрый старт

```bash
git clone https://github.com/alexkudelin/gost-pfx-divider.git
cd gost-pfx-divider

make build                      # собрать образ (один раз, ~2 минуты)
make split PFX=~/certs/ivanov.pfx
```

Пароль будет запрошен интерактивно, ввод не отображается:

```
Password for ivanov.pfx:
==> extracting private key
    /work/out/private.key  (Parameter set: id-GostR3410-2001-CryptoPro-A-ParamSet)
==> extracting certificate
    /work/out/public.cer  (subject=CN=Иванов Иван Иванович, O=ООО Ромашка, C=RU)
==> done
==> results in results/ivanov/
```

Либо неинтерактивно, через переменную окружения — для скриптов и CI:

```bash
export PFX_PASSWORD='...'
make split PFX=~/certs/ivanov.pfx
```

## Команды

Внешний `Makefile` — это интерфейс пользователя:

| Команда | Что делает |
| --- | --- |
| `make split PFX=file.pfx` | извлечь обе части |
| `make private PFX=file.pfx` | только приватный ключ |
| `make public PFX=file.pfx` | только сертификат |
| `make info PFX=file.pfx` | показать структуру контейнера и его алгоритмы, ничего не записывая |
| `make build` | собрать образ |
| `make rebuild` | пересобрать без кеша (подтянуть свежий gost-engine) |
| `make selftest` | проверить, что engine жив, на сгенерированном ГОСТ-контейнере |
| `make shell` | открыть shell внутри образа |
| `make clean` | удалить всё из `results/` (в терминале спросит подтверждение) |
| `make clean-image` | удалить образ |

`make build` вызывать необязательно: если образа нет, он соберётся при первом `make split`.

Полезно начинать с `make info` — он показывает, чем именно зашифрован ваш контейнер:

```
$ make info PFX=~/certs/ivanov.pfx
MAC: sha1, Iteration 2048
PKCS7 Encrypted data: pbeWithSHA1And40BitRC2-CBC, Iteration 2048
Certificate bag
PKCS7 Data
Shrouded Keybag: pbeWithSHA1And40BitRC2-CBC, Iteration 2048
```

## Результаты

Берётся имя PFX-файла, под ним создаётся каталог в `results/`, и туда кладутся обе части:

```
results/<имя pfx>/
├── private.key   PEM, без пароля, права 600
└── public.cer    PEM, права 644
```

Каталог `results/` целиком исключён из git-индекса — приватные ключи не попадут в репозиторий по невнимательности.

Файлы принадлежат вам, а не root: контейнер запускается с вашими UID и GID. Из PEM убраны служебные атрибуты `friendlyName` и `localKeyID`, которые КриптоПРО дописывает перед блоком и на которых спотыкаются некоторые парсеры — остаются чистые PEM-блоки.

В `public.cer` кладётся только сертификат владельца. Если в контейнере лежала цепочка УЦ, она не извлекается: для подключения к приложению нужен именно сертификат владельца, а корневые сертификаты обычно и так есть в хранилище.

### Как их использовать

```nginx
ssl_certificate     /etc/ssl/ivanov/public.cer;
ssl_certificate_key /etc/ssl/ivanov/private.key;
```

```bash
curl --cert public.cer --key private.key https://service.example.ru/
```

То есть ровно так же, как любую другую пару «ключ + сертификат». В этом и был смысл.

## Как это устроено

Два Makefile, разделённые границей контейнера:

```
Makefile                 внешний: интерфейс пользователя
└── docker/
    ├── Dockerfile       Debian trixie + OpenSSL 3.5 + gost-engine из исходников
    ├── openssl.cnf      включение engine gost и legacy provider
    ├── entrypoint.sh    читает пароль со stdin, кладёт в окружение
    └── Makefile         внутренний: собственно команды openssl
```

**Внешний Makefile** ничего не знает про OpenSSL. Он проверяет аргументы, добывает пароль, создаёт каталог результата и запускает контейнер: PFX монтируется read-only в `/work/input.pfx`, каталог результата — в `/work/out`.

**Внутренний Makefile** ничего не знает про Docker. Он принимает файл, пароль в `$PFX_PASSWORD` и каталог для результатов — а внутри у него прячутся четыре команды `openssl pkcs12`. Его можно прочитать за минуту и увидеть, что именно выполняется над вашим ключом; никакой магии там нет.

Ключевая часть — `docker/openssl.cnf`, где включены одновременно engine `gost` (ГОСТ-алгоритмы) и legacy provider (тот самый RC2). Это и есть та комбинация, из-за отсутствия которой «ничего не выходило».

Приватный ключ на промежуточном шаге пишется во временный файл внутри контейнера, а не в примонтированный каталог, и удаляется по `trap` даже при ошибке.

## Составные части

Проект — это обвязка вокруг чужой работы. Вот она:

* **[OpenSSL](https://github.com/openssl/openssl)** — [openssl.org](https://www.openssl.org/), Apache License 2.0. Используется версия 3.5.x из Debian trixie; требование задачи — 3.4 и новее.
* **[gost-engine](https://github.com/gost-engine/engine)** — реализация ГОСТ Р 34.10-2012, 34.11-2012, Магмы и Кузнечика для OpenSSL 3.x. Лицензия OpenSSL / Apache 2.0. Собирается из master при сборке образа.
* **[Debian](https://www.debian.org/)** trixie-slim в качестве базового образа.

Спасибо их авторам — вся содержательная криптография здесь их.

## Безопасность

* `private.key` выгружается **без пароля**, чтобы его можно было сразу подключить к приложению. Это обычный, но чувствительный файл: он создаётся с правами 600, храните его соответственно и не коммитьте.
* Пароль от PFX передаётся через stdin и не появляется ни в аргументах, ни в переменных окружения контейнера, ни в истории shell (если задавать его интерактивно).
* Контейнер работает без сети (`--network none`) и без прав root.
* PFX монтируется только на чтение — исходный контейнер невозможно повредить.
* Ключи остаются на вашей машине. Проект ничего никуда не отправляет.
